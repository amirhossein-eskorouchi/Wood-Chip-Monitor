# Model Artifacts

Wood-Chip Monitor uses optimized deep-learning models for real-time edge inference on NVIDIA Jetson hardware.

The system contains two primary vision components:

1. **Wood-chip detection and geometric measurement**
2. **Wood-chip moisture assessment**

The large model binaries used during deployment are intentionally **not stored in this GitHub repository**. TensorRT engine files are deployment artifacts that depend on the target NVIDIA hardware and software environment and should therefore be generated for the target device.

---

## Expected Model Directory

By default, the application expects the following structure:

```text
models/
├── detr_resnet101_fp16.engine
├── moistnetlite_fp16.engine
└── moistnetlite_classes.txt
```

The default paths can be overridden through environment variables when the models are stored elsewhere.

---

## Wood-Chip Detection Model

The detection component identifies individual wood chips in the camera stream and provides the bounding-box information required for downstream quality analytics.

The deployed detector is used to support:

- dense wood-chip localization,
- physical chip-size estimation,
- size-distribution monitoring,
- oversize-chip identification,
- and real-time visualization in the operator dashboard.

The default deployment artifact is:

```text
detr_resnet101_fp16.engine
```

This is a TensorRT FP16 engine prepared for edge inference.

The underlying research on distribution-aware wood-chip detection and size-distribution estimation is maintained separately in the **UOT-DETR** repository:

https://github.com/amirhossein-eskorouchi/UOT-DETR

Keeping the research implementation separate from the monitoring application avoids duplicating the full training and experimental framework inside this deployment repository.

---

## Moisture Assessment Model

Wood-Chip Monitor also integrates a lightweight vision model for image-based moisture assessment.

The deployed model processes selected wood-chip image regions and provides moisture-related predictions alongside the geometric quality measurements generated by the detection pipeline.

The default deployment artifact is:

```text
moistnetlite_fp16.engine
```

The corresponding class definitions are expected in:

```text
moistnetlite_classes.txt
```

The class file should contain the moisture categories expected by the deployed model.

Additional methodological and publication information for the moisture-assessment model will be linked from the main project documentation.

## Configuring Model Paths

The application searches the repository's `models/` directory by default.

Model locations can be changed without modifying the source code by setting environment variables.

### Default model directory

```bash
export WOODCHIP_MODEL_DIR=/path/to/models
```

### Detection engine

```bash
export WOODCHIP_DETR_ENGINE=/path/to/detr_resnet101_fp16.engine
```

### Moisture engine

```bash
export WOODCHIP_MOISTURE_ENGINE=/path/to/moistnetlite_fp16.engine
```

### Moisture class file

```bash
export WOODCHIP_MOISTURE_CLASSES=/path/to/moistnetlite_classes.txt
```

An example device configuration is provided in:

```text
configs/device.env.example
```

## Why TensorRT Engines Are Not Included

TensorRT `.engine` files should generally not be treated as portable model binaries.

An engine generated on one machine may not be compatible with another system because compatibility can depend on factors such as:

- NVIDIA GPU architecture,
- JetPack version,
- CUDA version,
- cuDNN version,
- TensorRT version,
- precision mode,
- optimization profiles,
- and model input dimensions.

For reproducible deployment, engines should be generated or validated within the intended target environment.

This repository therefore treats TensorRT engines as **local deployment artifacts**, rather than canonical research files.

The intended deployment workflow is:

```text
Training checkpoint
        │
        ▼
   PyTorch model
        │
        ▼
      ONNX
        │
        ▼
 TensorRT engine
        │
        ▼
Wood-Chip Monitor
```

Model-export and TensorRT conversion utilities will be maintained in the repository's deployment/tooling components.

Detailed instructions will be provided in the deployment documentation.

## Precision

The original edge deployment uses FP16 TensorRT inference where supported.

The expected detector engine name therefore includes:

```text
fp16
```

as in:

```text
detr_resnet101_fp16.engine
```

The moisture model follows the same convention:

```text
moistnetlite_fp16.engine
```

Engine precision and optimization settings should be selected according to the capabilities of the target device.

## Model Files and Git

Large or machine-specific model artifacts are excluded from version control.

The repository `.gitignore` excludes files such as:

```text
*.engine
*.onnx
*.pt
*.pth
*.ckpt
*.trt
*.weights
```

This prevents trained weights, intermediate exports, and device-specific TensorRT engines from being committed accidentally.

The `models/` directory is retained in the repository through this README so that users know where local deployment artifacts should be placed.

---

## Deployment Checklist

Before starting Wood-Chip Monitor on a target device, verify that:

- the detection TensorRT engine is available,
- the moisture TensorRT engine is available,
- the moisture class file is available,
- model paths are configured correctly,
- TensorRT can deserialize both engines,
- the expected input dimensions match the deployed models,
- and the target Jetson environment is compatible with the generated engines.

Device-specific setup instructions are maintained in the project documentation.

## Research vs. Deployment Artifacts

This repository focuses on **system integration and edge deployment**.

The complete research code used to train, benchmark, and evaluate the underlying detection methodology is intentionally maintained separately.

In particular:

- **UOT-DETR repository:** research implementation, experiments, benchmarks, and reproducibility
- **Wood-Chip Monitor repository:** edge inference, system integration, analytics, dashboard, and deployment

This separation keeps the monitoring system focused while preserving a clear connection to the underlying research.

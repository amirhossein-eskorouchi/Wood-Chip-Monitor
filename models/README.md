# Model Artifacts

Wood-Chip Monitor uses optimized deep-learning models for real-time edge inference on NVIDIA Jetson hardware.

The system contains two primary vision components:

1. **Wood-chip detection and geometric measurement**
2. **Wood-chip moisture assessment**

The trained weights and TensorRT engine files used during deployment are intentionally **not stored in this GitHub repository**. TensorRT engines are deployment artifacts that depend on the target NVIDIA hardware and software environment and should therefore be generated or validated for the intended device.

## Wood-Chip Detection Model

The detection component identifies individual wood chips in the camera stream and provides the bounding-box information required for downstream quality analytics.

The deployed detector supports:

- dense wood-chip localization,
- physical chip-size estimation,
- rolling size-distribution analysis,
- oversize-chip identification,
- chip-region extraction for moisture assessment,
- and real-time visualization in the operator dashboard.

The default deployment artifact is:

```text
detr_resnet101_fp16.engine
```

This is a TensorRT FP16 engine prepared for edge inference.

The underlying detector is part of the broader research effort on distribution-aware wood-chip detection and size-distribution estimation.

The complete research implementation, experimental framework, benchmarks, ablation studies, and reproducibility resources are maintained separately in the **UOT-DETR** repository:

https://github.com/amirhossein-eskorouchi/UOT-DETR

Keeping the research implementation separate from Wood-Chip Monitor avoids duplicating the full training and experimental framework inside this deployment-focused repository.

## MoistNetLite

Wood-Chip Monitor integrates **MoistNetLite**, a lightweight convolutional neural network for image-based wood-chip moisture assessment.

The model architecture is provided in:

```text
models/moistnetlite.py
```

MoistNetLite operates on selected wood-chip image regions extracted from detector outputs and provides moisture-condition predictions alongside the geometric measurements generated by the detection pipeline.

The architecture uses:

- convolutional feature extraction,
- max-pooling,
- dropout regularization,
- global average pooling,
- a compact dense representation,
- and a three-class classification head.

The model accepts RGB image regions with an expected input size of:

```text
224 Ã— 224 Ã— 3
```

and produces predictions for three moisture-condition categories.

The deployed TensorRT artifact is expected to be:

```text
moistnetlite_fp16.engine
```

The associated class definitions are expected in:

```text
moistnetlite_classes.txt
```

The class file should contain the moisture categories expected by the deployed model.

## Configuring Model Paths

The application searches the repository's `models/` directory by default.

Model locations can be changed without modifying the source code by setting environment variables.

### Default model directory

```bash
export WOODCHIP_MODEL_DIR=/path/to/models
```

### Detection engine

```bash
export WOODCHIP_DETR_ENGINE=/path/to/detr_resnet101_fp16.engine
```

### Moisture engine

```bash
export WOODCHIP_MOISTURE_ENGINE=/path/to/moistnetlite_fp16.engine
```

### Moisture class file

```bash
export WOODCHIP_MOISTURE_CLASSES=/path/to/moistnetlite_classes.txt
```

An example device configuration is provided in:

```text
configs/device.env.example
```

Users should copy or adapt that configuration for the target Jetson device rather than editing machine-specific paths directly inside the source code.

## Why TensorRT Engines Are Not Included

TensorRT `.engine` files should not generally be treated as portable model binaries.

An engine generated in one environment may not be compatible with another system because compatibility can depend on factors such as:

- NVIDIA GPU architecture,
- JetPack version,
- L4T version,
- CUDA version,
- cuDNN version,
- TensorRT version,
- precision mode,
- optimization profiles,
- model input dimensions,
- and engine-building configuration.

For reproducible deployment, TensorRT engines should therefore be generated or validated within the intended target environment.

This repository treats TensorRT engines as **local deployment artifacts**, rather than canonical research files.

## Detection Engine

The default detector engine is named:

```text
detr_resnet101_fp16.engine
```

The `fp16` suffix indicates that the reference deployment uses FP16 TensorRT inference where supported by the target hardware and TensorRT environment.

The detector receives preprocessed camera frames and produces the DETR outputs required for subsequent filtering and geometric analysis.

The application runtime handles:

1. image preprocessing,
2. TensorRT inference,
3. confidence filtering,
4. bounding-box processing,
5. physical measurement,
6. quality analytics,
7. visualization.


This utility can be used to test the detector on image files independently of the full live-monitoring application.

## Precision

The original edge deployment uses FP16 TensorRT inference where supported.

The expected detector engine therefore follows the naming convention:

```text
detr_resnet101_fp16.engine
```

The moisture model follows the same convention:

```text
moistnetlite_fp16.engine
```

Engine precision and optimization settings should be selected according to the capabilities of the target NVIDIA device.

The repository does not assume that an engine generated for one device or TensorRT environment is automatically compatible with another.

## Model Files and Git

Large or machine-specific model artifacts are excluded from version control.

The repository `.gitignore` excludes files such as:

```text
*.engine
*.onnx
*.pt
*.pth
*.ckpt
*.trt
*.weights
```

This prevents:

- trained model weights,
- intermediate exports,
- ONNX artifacts,
- TensorRT engines,
- and other large deployment binaries

from being committed accidentally.

The `models/` directory remains part of the repository through this README and the MoistNetLite architecture definition so that users know where local deployment artifacts should be placed.

## Deployment Checklist

Before starting Wood-Chip Monitor on a target device, verify that:

- the detection TensorRT engine is available,
- the moisture TensorRT engine is available,
- the moisture class file is available,
- model paths are configured correctly,
- TensorRT can deserialize both engines,
- the detector output bindings match the runtime expectations,
- the expected input dimensions match the deployed models,
- the class ordering matches the MoistNetLite engine,
- the target CUDA/TensorRT environment is compatible with the generated engines,
- and sufficient device memory is available for both inference components.

## Reproducibility Notes

The reference Wood-Chip Monitor prototype was developed on an NVIDIA Jetson Nano using a legacy Jetson software environment.

TensorRT model reproducibility therefore depends on both the model definition and the deployment software stack.

The repository intentionally distinguishes between:

1. **source architecture**, which can be version-controlled,
2. **trained weights**, which may be distributed separately,
3. **intermediate model formats**, such as ONNX,
4. **device-specific TensorRT engines**, which should be generated or validated for the target environment.

This distinction helps avoid presenting a device-specific binary as though it were universally portable.
